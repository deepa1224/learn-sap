Chapter 01

Introduction to SAP HANA 2.0

SAP HANA is an in-memory, column-oriented relational database management system. Understanding its core architecture is the foundation for everything that follows.

🏛️ What is SAP HANA?

▼

SAP HANA (High-performance ANalytic Appliance) is an in-memory database platform that combines OLAP (Online Analytical Processing) and OLTP (Online Transaction Processing) in a single system. Unlike traditional disk-based databases, HANA stores all data in RAM, enabling query performance measured in milliseconds rather than seconds.

Key Concept

HANA uses column-based storage by default. Instead of storing data row-by-row (like traditional RDBMS), it stores each column contiguously in memory. This allows massive compression ratios (often 5:1 to 10:1) and blazing-fast analytical aggregations because the engine only reads the columns it needs.

SAP HANA 2.0, released in November 2016, introduced multi-tenant database containers, enhanced high availability, and improved integration with cloud platforms. It serves as the database layer for SAP S/4HANA, SAP BW/4HANA, and many other SAP applications.

🧩 HANA 2.0 Architecture Overview

▼

SAP HANA has a layered architecture consisting of multiple services, each handling a specific responsibility. The Index Server is the core — it manages data storage, query processing, and transaction management.

SAP HANA 2.0 Service Architecture

Index Server is the heart. It holds the in-memory column store, processes SQL, and manages transactions. The Name Server maintains the system landscape and configuration. In scale-out scenarios, it coordinates which host handles which data partition.

Pro Tip for Admins

Use HDB info from the command line to see which services are running and their process IDs. Use sapcontrol -nr <instance> -function GetProcessList for programmatic checks in scripts and monitoring.

Chapter 02

Planning & Sizing

Before installing HANA, you must correctly size hardware and plan your landscape. Getting this wrong is the most expensive mistake you can make.

📐 Hardware Sizing Fundamentals

▼

Sizing SAP HANA means determining the amount of memory (RAM) your system needs. HANA is memory-bound — CPU and disk are secondary considerations. All active data must fit in RAM.

Key Concept — The Sizing Formula

Required RAM = (Disk DB size on source ÷ Compression Factor) + Working Memory. For a BW on HANA migration, expect 5:1 compression. For S/4HANA, use the SAP Sizing Report (transaction /SDF/HDB_SIZING on the source system).

ComponentSizing Rule
Data in memorySource DB size ÷ compression ratio (typically 3–7x)
Working memory~50% of data memory (for processing)
OS + Services~50 GB reserved for HANA services & OS
Disk: Data volumes4× RAM (for savepoints & snapshots)
Disk: Log volumes1× RAM (minimum), on separate fast disk

Common Mistake

Never size based solely on current disk usage. You must account for data growth over 3–5 years, seasonal peak loads, and shadow tables. Always add a 20–30% buffer above the calculated RAM requirement.

🗺️ Landscape Planning

▼

A standard SAP landscape consists of Development (DEV), Quality Assurance (QAS), and Production (PRD) systems. HANA 2.0's multi-tenant database container (MDC) architecture lets you consolidate multiple databases on a single HANA instance.

Key Concept — Scale-Up vs Scale-Out

Scale-Up: Single server with maximum RAM (up to 24 TB on certified hardware). Best for most workloads. Scale-Out: Multiple servers forming a distributed HANA system. Use only when a single server cannot hold all data. Scale-out adds complexity in administration, networking, and failover.

Decisions to make during landscape planning:

  1. Single-tenant vs multi-tenant database container (MDC) deployment
  2. Scale-up vs scale-out topology
  3. High Availability: HANA System Replication (HSR) vs storage-based replication
  4. Disaster Recovery strategy and RPO/RTO targets
  5. Network segmentation: client, internal, replication, and storage networks

📦 HDBLCM Installation Walkthrough

▼

The HANA Database Lifecycle Manager (HDBLCM) is the official tool for installing, updating, and managing SAP HANA. It provides both a GUI (browser-based) and a CLI.

  1. Download SAP HANA installation media from SAP Software Download Center (support.sap.com)
  2. Extract the archive: tar -xvzf IMDB_SERVER*.SAR
  3. Run the installer as root: ./hdblcm --action=install
  4. Enter SID (System ID) — 3 characters, uppercase: e.g., HDB
  5. Enter instance number (00-97): e.g., 00
  6. Set the SYSTEM user password (strong, min 8 chars)
  7. Choose components: server, AFL, EML, client, etc.
  8. Specify data and log volume paths (should be on separate file systems)
  9. Confirm and start installation (typically 15–30 minutes)
# Interactive installation ./hdblcm --action=install # Silent installation with config file ./hdblcm --action=install \ --configfile=hana_install.cfg \ --batch # Key post-install validation su - hdbadm HDB info # Check all processes running hdbsql -i 00 -u SYSTEM # Connect to verify SQL access SELECT * FROM M_DATABASE; # Verify database info

Pro Tip

For automated deployments (e.g., Terraform, Ansible), use the --batch flag with a configuration file. Generate a template config with ./hdblcm --action=install --dump_configfile_template=template.cfg. This is essential for consistent, repeatable installations across environments.

✅ Post-Installation Checks

▼

After installation, validate the system thoroughly before declaring it ready:

# 1. Check running services HDB info # 2. Verify system DB connectivity hdbsql -i 00 -d SYSTEMDB -u SYSTEM \ "SELECT * FROM SYS.M_SERVICES" # 3. Check memory allocation hdbsql -i 00 -u SYSTEM \ "SELECT HOST, USED_PHYSICAL_MEMORY, FREE_PHYSICAL_MEMORY FROM SYS.M_HOST_RESOURCE_UTILIZATION" # 4. Verify license hdbsql -i 00 -u SYSTEM \ "SELECT * FROM M_LICENSE" # 5. Check alerts hdbsql -i 00 -u SYSTEM \ "SELECT * FROM _SYS_STATISTICS.STATISTICS_CURRENT_ALERTS"

Key Concept — Instance Numbers & Ports

SAP HANA uses a port numbering scheme based on the instance number. For instance 00: SQL port = 30015 (for system DB) or 30013 (for MDC tenant DB via SQL/MDX). The general formula is: 3<instance>13 for the SQL port and 3<instance>15 for the internal port. Know these by heart.

Chapter 05

Multi-Tenant Database Containers

MDC is a game-changer in HANA 2.0 — run multiple isolated databases on a single HANA system, each with its own users, data, and backups.

📦 Understanding MDC Architecture

▼

In HANA 2.0, every installation is an MDC system, even if you only use one tenant database. The architecture consists of:

MDC Architecture: One system, multiple isolated tenant databases

SYSTEMDB is a special database used only for system administration — creating/deleting tenants, managing system replication, and monitoring. Your application data lives in tenant databases. Each tenant is fully isolated: separate memory space, separate backups, separate users.

# Create a new tenant database hdbsql -i 00 -d SYSTEMDB -u SYSTEM CREATE DATABASE DEV SYSTEM USER PASSWORD "SecurePass123!"; # List all tenant databases SELECT DATABASE_NAME, ACTIVE_STATUS FROM SYS.M_DATABASES; # Connect directly to a tenant hdbsql -i 00 -d PRD -u SYSTEM # Stop a specific tenant (from SYSTEMDB) ALTER DATABASE DEV STOP;

Chapter 07

Memory Management

Memory is the lifeblood of SAP HANA. Understanding how HANA allocates, uses, and manages memory is the most critical skill for an administrator.

🧠 Memory Architecture

▼

HANA's memory model has several layers:

SAP HANA Memory Model — Layered Architecture

Key Concept — Allocation Limit

The global_allocation_limit parameter (in global.ini → [memorymanager]) sets the maximum memory HANA is allowed to use. Set this to 90% of physical RAM to leave room for the OS. If HANA exceeds this limit, it triggers Out-of-Memory (OOM) handling which kills expensive statements or ultimately crashes the system.

# Check current memory usage SELECT HOST, ROUND(USED_PHYSICAL_MEMORY/1024/1024/1024, 2) AS "Used_GB", ROUND(FREE_PHYSICAL_MEMORY/1024/1024/1024, 2) AS "Free_GB", ROUND(INSTANCE_TOTAL_MEMORY_USED_SIZE/1024/1024/1024, 2) AS "HANA_Used_GB", ROUND(ALLOCATION_LIMIT/1024/1024/1024, 2) AS "Alloc_Limit_GB" FROM SYS.M_HOST_RESOURCE_UTILIZATION; # Memory by component SELECT COMPONENT, ROUND(USED_MEMORY_SIZE/1024/1024/1024, 2) AS "Used_GB" FROM SYS.M_SERVICE_COMPONENT_MEMORY ORDER BY USED_MEMORY_SIZE DESC;

OOM Emergency Response

When HANA runs low on memory: (1) It first kills the most expensive running statements. (2) Then it unloads column store tables marked as unloadable. (3) If that's not enough, it may crash. Always monitor the M_HOST_RESOURCE_UTILIZATION view and set up alerts at 80% and 90% of the allocation limit.

🧊 Native Storage Extension (NSE)

▼

NSE (introduced in SPS 03) allows you to move "warm" data (infrequently accessed but occasionally queried) from in-memory to disk-based storage, while keeping "hot" data in RAM. This dramatically reduces memory costs.

# Enable NSE on a column store table ALTER TABLE my_schema.large_history_table PAGE LOADABLE; # Move it back to in-memory (column loadable) ALTER TABLE my_schema.large_history_table COLUMN LOADABLE; # Check which tables use NSE SELECT SCHEMA_NAME, TABLE_NAME, LOAD_UNIT FROM SYS.TABLES WHERE LOAD_UNIT = 'PAGE';

Key Concept

COLUMN LOADABLE = traditional in-memory (fast, expensive). PAGE LOADABLE = NSE disk-based with buffer cache (slower queries, much less RAM). Use NSE for audit logs, historical data, and large tables accessed less than daily. A good rule of thumb: if a table is accessed less than once per hour, consider NSE.

Check Your Understanding

What should you set the global_allocation_limit to?
100% of physical RAM

50% of physical RAM
Equal to the data size on disk
✅ Set it to approximately 90% of physical RAM. The remaining 10% is reserved for the operating system, OS file cache, and non-HANA processes. Setting it to 100% risks OS-level OOM kills.
Chapter 08

Backup & Recovery

Backups are your insurance policy. HANA offers flexible backup strategies — file-based, third-party tools (Backint), and storage snapshots. Master all of them.

💾 Backup Types & Strategy

▼
Backup TypeWhat It CapturesWhen to Use
Complete DataAll data + redo logs since last savepointWeekly or nightly — your baseline
DifferentialChanges since last full backupDaily between full backups
IncrementalChanges since last any backupHourly for critical systems
Log (continuous)Transaction redo logsAlways ON — enables point-in-time recovery
# Full backup via SQL BACKUP DATA USING FILE ('/hana/backup/data/FULL'); # Differential backup BACKUP DATA DIFFERENTIAL USING FILE ('/hana/backup/data/DIFF'); # Incremental backup BACKUP DATA INCREMENTAL USING FILE ('/hana/backup/data/INCR'); # Enable log backup (CRITICAL — must be enabled!) ALTER SYSTEM ALTER CONFIGURATION ('global.ini', 'SYSTEM') SET ('persistence', 'log_mode') = 'normal'; # Set log backup interval (every 15 minutes) ALTER SYSTEM ALTER CONFIGURATION ('global.ini', 'SYSTEM') SET ('persistence', 'log_backup_interval_s') = '900'; # Check backup catalog SELECT BACKUP_ID, UTC_START_TIME, ENTRY_TYPE_NAME, STATE_NAME FROM SYS.M_BACKUP_CATALOG ORDER BY UTC_START_TIME DESC;

Critical

Log mode must be set to normal (not overwrite) for production systems. Without log backups, you can only recover to the last full/differential backup — losing all transactions since then. Log segments also fill up and eventually halt the database if not backed up.

🔄 Recovery Procedures

▼

Recovery scenarios you must be prepared for:

  1. Point-in-time recovery — Recover to a specific timestamp (requires log backups)
  2. Most recent state — Recover everything up to the last committed transaction
  3. Specific backup — Recover from a particular backup ID
  4. Tenant-specific recovery — In MDC, you can recover individual tenants without affecting others
# Recovery to most recent state RECOVER DATA USING FILE ('/hana/backup/data/FULL') CLEAR LOG; # Point-in-time recovery RECOVER DATABASE UNTIL TIMESTAMP '2024-06-15 14:30:00' USING FILE ('/hana/backup/data/FULL') USING LOG PATH ('/hana/backup/log') CLEAR LOG; # Recovery of a specific tenant (from SYSTEMDB) RECOVER DATABASE FOR PRD UNTIL TIMESTAMP '2024-06-15 14:30:00' USING FILE ('/hana/backup/data/FULL') USING LOG PATH ('/hana/backup/log') CLEAR LOG;

Pro Tip

Test your recovery procedures at least quarterly. Create a documented Recovery Runbook with step-by-step procedures for each scenario. Time your recovery — know how long a full restore takes so you can set realistic RTO expectations with stakeholders.

Chapter 09

High Availability & Disaster Recovery

HANA System Replication (HSR) is your primary tool for HA and DR. Understand the replication modes, takeover procedures, and cluster integration.

🔗 HANA System Replication (HSR)

▼

HSR continuously replicates data from a primary to a secondary HANA system. It operates at the persistence layer, shipping redo log buffers from primary to secondary.

Replication ModeData Loss RiskPerformance ImpactUse Case
SYNCZero (RPO = 0)Higher latencyHA — same datacenter
SYNCMEMNear-zeroModerateHA — same datacenter
ASYNCPossible (seconds)MinimalDR — remote datacenter
# ── On PRIMARY system (as <sid>adm) ── # Enable system replication hdbnsutil -sr_enable --name=DC1_PRIMARY # ── On SECONDARY system (as <sid>adm) ── # Stop the instance first HDB stop # Register as secondary hdbnsutil -sr_register \ --name=DC2_SECONDARY \ --remoteHost=hana-primary \ --remoteInstance=00 \ --replicationMode=syncmem \ --operationMode=logreplay # Start the secondary HDB start # ── Check replication status ── hdbnsutil -sr_state # Or via SQL on primary: SELECT * FROM SYS.M_SERVICE_REPLICATION;

Key Concept — Operation Modes

logreplay: Secondary replays logs as they arrive — the secondary is always in recovery mode. logreplay_readaccess: Same, but allows read-only SQL access to the secondary (Active/Active read-enabled). delta_datashipping: Periodic full data shipping — legacy, rarely used. Always prefer logreplay for performance.

Dig Deeper

  • Multi-tier replication — Chain replication: Primary → Secondary (sync) → Tertiary (async for DR)
  • Multi-target replication (SPS 05+) — Primary replicates to multiple secondaries simultaneously
  • Cluster integration — Use Pacemaker/SUSE HAE or RHEL HA Add-on for automated failover with SAPHanaSR resource agents
  • SAP Note 1999880 — FAQ on HANA System Replication

⚡ Takeover Procedures

▼
# ── Manual takeover (planned) ── # On SECONDARY: hdbnsutil -sr_takeover # ── Forced takeover (primary is down) ── hdbnsutil -sr_takeover --force # ── After takeover: re-register old primary as new secondary ── # On OLD PRIMARY (now becoming secondary): HDB stop hdbnsutil -sr_register \ --name=DC1_PRIMARY \ --remoteHost=hana-secondary \ --remoteInstance=00 \ --replicationMode=syncmem \ --operationMode=logreplay HDB start

Critical for Production

Always test takeover procedures before going live. Document the exact sequence: (1) verify secondary is synchronized, (2) perform takeover, (3) switch application connections (virtual IP/hostname), (4) verify application connectivity, (5) re-register old primary. Practice until your team can execute this in under 15 minutes.

Chapter 10

Performance Monitoring & Optimization

Performance tuning in HANA focuses on SQL optimization, memory management, and understanding the workload. Your most powerful tools are the monitoring views.

📊 Essential Monitoring Views

▼

HANA's SYS.M_* monitoring views are your Swiss Army knife. Here are the ones you should query daily:

# ── Top 10 most expensive SQL statements ── SELECT TOP 10 STATEMENT_HASH, EXECUTION_COUNT, ROUND(TOTAL_EXECUTION_TIME/1000000, 2) AS "Total_Sec", ROUND(AVG_EXECUTION_TIME/1000, 2) AS "Avg_ms", TOTAL_LOCK_WAIT_COUNT, STATEMENT_STRING FROM SYS.M_SQL_PLAN_CACHE ORDER BY TOTAL_EXECUTION_TIME DESC; # ── Currently running expensive statements ── SELECT CONNECTION_ID, STATEMENT_ID, ROUND(DURATION/1000000, 2) AS "Duration_Sec", ALLOCATED_MEMORY_SIZE/1024/1024 AS "Mem_MB", STATEMENT_STRING FROM SYS.M_EXPENSIVE_STATEMENTS WHERE STATUS = 'EXECUTING' ORDER BY DURATION DESC; # ── Table sizes and memory consumption ── SELECT SCHEMA_NAME, TABLE_NAME, ROUND(MEMORY_SIZE_IN_TOTAL/1024/1024, 2) AS "Total_MB", RECORD_COUNT, LOAD_UNIT FROM SYS.M_CS_TABLES ORDER BY MEMORY_SIZE_IN_TOTAL DESC FETCH FIRST 20 ROWS ONLY; # ── Blocked transactions ── SELECT * FROM SYS.M_BLOCKED_TRANSACTIONS; # ── Disk space usage ── SELECT HOST, USAGE_TYPE, ROUND(TOTAL_SIZE/1024/1024/1024, 2) AS "Total_GB", ROUND(USED_SIZE/1024/1024/1024, 2) AS "Used_GB" FROM SYS.M_DISKS;

Pro Tip

Create a "Daily Health Check" SQL script that queries all these views and outputs a concise report. Schedule it via a cron job or HANA's built-in job scheduler. Over time, these daily snapshots become invaluable for spotting trends (growing tables, degrading query times, memory creep).

🔧 SQL Tuning Techniques

▼

Key optimization strategies for HANA SQL:

Key Concept — EXPLAIN PLAN

Always start with EXPLAIN PLAN FOR <your_query>. Look for full table scans on large tables (should be column scans or index lookups), excessive data transfer between nodes (in scale-out), and large intermediate result sets. The plan visualizer in HANA Cockpit or Studio shows this graphically.

Common tuning actions:

  1. Use the right store — Analytical queries on column store, heavy single-row lookups on row store
  2. Partition large tables — Hash, range, or round-robin partitioning distributes load
  3. Push down calculations — Use calculation views and SQL functions instead of pulling data to the application layer
  4. Avoid SELECT * — Column store benefits most when you select only needed columns
  5. Monitor delta merge — Unmerged delta stores degrade query performance
# Check delta merge status for a table SELECT SCHEMA_NAME, TABLE_NAME, RAW_RECORD_COUNT_IN_DELTA, RECORD_COUNT_IN_MAIN, LAST_MERGE_TIME FROM SYS.M_CS_TABLES WHERE RAW_RECORD_COUNT_IN_DELTA > 1000000; # Trigger a manual delta merge MERGE DELTA OF my_schema.my_table;

Configuration Management

HANA configuration is stored in INI files with a layered hierarchy. Understanding how configuration layers work prevents mysterious behavior.

📝 Configuration Layers & INI Files

▼

HANA configuration follows a hierarchy — higher layers override lower ones:

  1. DEFAULT — Built-in defaults (cannot be changed)
  2. SYSTEM — System-wide settings (apply to all hosts)
  3. HOST — Host-specific overrides (for individual servers)
  4. DATABASE — Tenant-specific settings (in MDC)

Key INI files you'll work with regularly:

FileControls
global.iniMemory limits, persistence, backup, auditing
indexserver.iniSQL processing, joins, communication, SSL
nameserver.iniTopology, password policy, landscape
daemon.iniInstance startup, services to run
xsengine.iniXS Advanced settings
# View a configuration parameter SELECT * FROM SYS.M_INIFILE_CONTENTS WHERE FILE_NAME = 'global.ini' AND SECTION = 'memorymanager'; # Change a system-level parameter ALTER SYSTEM ALTER CONFIGURATION ('global.ini', 'SYSTEM') SET ('memorymanager', 'global_allocation_limit') = '920000'; # Change a host-level parameter ALTER SYSTEM ALTER CONFIGURATION ('indexserver.ini', 'HOST', 'hana01') SET ('joins', 'max_concurrency') = '0'; # Reset to default (remove override) ALTER SYSTEM ALTER CONFIGURATION ('global.ini', 'SYSTEM') UNSET ('memorymanager', 'global_allocation_limit');

Important

Never edit INI files directly on disk. Always use SQL ALTER SYSTEM ALTER CONFIGURATION or the HANA Cockpit. Direct file edits may be overwritten, may not take effect until restart, and bypass the configuration change audit trail.

Data Provisioning & Integration

Getting data into HANA efficiently is critical. HANA supports real-time replication, ETL, and smart data access for federated queries.

▼

# Import CSV data IMPORT FROM CSV FILE '/hana/data/import/customers.csv' INTO my_schema.customers WITH RECORD DELIMITED BY '\n' FIELD DELIMITED BY ',' THREADS 10 BATCH 10000; # Create a remote source (Smart Data Access) CREATE REMOTE SOURCE my_oracle ADAPTER "odbc" CONFIGURATION 'DSN=ORA_PROD' WITH CREDENTIAL TYPE 'PASSWORD' USING 'user=sap_read;password=***'; # Query remote data as if it were local SELECT * FROM my_oracle.ORACLE_SCHEMA.REMOTE_TABLE;

Pro Tip

For large initial data loads (100 GB+), use the IMPORT FROM statement with the THREADS parameter set to the number of CPU cores available. This parallelizes the load and can achieve throughput of 1+ TB/hour on modern hardware. Disable logging during initial load with ALTER TABLE ... DISABLE LOG (remember to re-enable after!).

Chapter 14

Troubleshooting

When things go wrong — and they will — you need a systematic approach. Trace files, diagnostic views, and SAP support tools are your weapons.

🔍 Diagnostic Methodology

▼

Follow this systematic approach when troubleshooting:

  1. Check alerts first — SELECT * FROM _SYS_STATISTICS.STATISTICS_CURRENT_ALERTS WHERE ALERT_RATING >= 3
  2. Review trace files — /usr/sap/<SID>/HDB<inst>/<host>/trace/ — look for indexserver_alert_<host>.trc
  3. Check system availability — M_SERVICE_STATISTICS for restart timestamps
  4. Analyze resource usage — Memory, CPU, disk from monitoring views
  5. Check expensive statements — Often performance issues are caused by a single bad query
  6. Review configuration changes — M_INIFILE_CONTENT_HISTORY for recent config changes
# ── Troubleshooting command toolkit ── # Check for recent crashes/restarts SELECT HOST, SERVICE_NAME, ACTIVE_STATUS, START_TIME, COORDINATOR_TYPE FROM SYS.M_SERVICES WHERE ACTIVE_STATUS != 'YES'; # View current alerts SELECT ALERT_ID, ALERT_RATING, ALERT_NAME, ALERT_DETAILS, ALERT_TIMESTAMP FROM _SYS_STATISTICS.STATISTICS_CURRENT_ALERTS WHERE ALERT_RATING >= 3 ORDER BY ALERT_TIMESTAMP DESC; # Check for long-running transactions SELECT CONNECTION_ID, TRANSACTION_ID, UPDATE_TRANSACTION_ID, ROUND(IDLE_TIME/1000, 0) AS "Idle_Sec" FROM SYS.M_TRANSACTIONS WHERE IDLE_TIME > 3600000; -- idle > 1 hour # Generate a full system report (Mini Check) # Download SAP HANA Mini Check SQL from SAP Note 1969700 # Run it via: hdbsql -i 00 -d SYSTEMDB -u SYSTEM -I minicheck.sql

Dig Deeper

  • SAP Note 1969700 — SQL Statement Collection for HANA (the "Mini Check" — essential!)
  • SAP Note 2000000 — How to analyze SAP HANA trace files
  • HANA Support Ticket Checklist — Always include: HANA version (HDB version), SPS level, full trace files, and Mini Check output when opening SAP incidents
  • Full System Info Collection — Use hdbcons 'runtimedump full' for deep system diagnostics
Chapter 15

Updates, Patches & Lifecycle Management

Keeping HANA current is not optional. Security patches, bug fixes, and performance improvements require a disciplined update strategy.

🔄 Update & Upgrade Procedures

▼

HANA updates come in two forms: Revision updates (minor, within same SPS — e.g., SPS 05 Rev 59.00 → Rev 59.04) and SPS upgrades (major — e.g., SPS 05 → SPS 06).

# Check current version HDB version # Or via SQL: SELECT VERSION FROM SYS.M_DATABASE; # Update using HDBLCM ./hdblcm --action=update \ --component_dirs=/hana/shared/media/SAP_HANA_DATABASE \ --batch # With HSR: Update secondary first, takeover, then update old primary # This achieves near-zero downtime updates!
  1. Pre-update: Full backup, check SAP Notes for known issues, verify disk space (2× installation size free)
  2. Test first: Always apply updates to DEV/QAS before production
  3. For HSR systems: Update secondary → verify replication → takeover → update old primary → re-register
  4. Post-update: Run Mini Check, verify all services running, check application connectivity

Pro Tip

Subscribe to SAP HANA Release Notes on SAP Support Portal. Create a standing change request template for HANA updates so the process is streamlined. Build an automated pre-check script that validates: disk space, current backup status, replication state, and running jobs before each update.

Final Knowledge Check

In an HSR environment, what's the correct order for a near-zero downtime update?
Update primary → takeover → update secondary
Update secondary → takeover → update old primary
Stop both → update both simultaneously → start both
Deregister HSR → update primary only → re-register
✅ Update secondary first while primary continues serving. Then perform a takeover so the updated secondary becomes the new primary. Finally, update the old primary and re-register it as the new secondary. This minimizes downtime to just the takeover window (typically seconds to minutes).
