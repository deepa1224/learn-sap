Chapter 0

Why does SAP BTP exist?

Before BTP, enterprises faced a painful set of interconnected problems. Understanding these problems is the key to understanding every design decision SAP made.

🔒

The Upgrade Trap

Companies modified SAP core code (custom ABAP, user exits, BAdIs with internal tables). Every upgrade became a multi-month, multi-million-dollar regression nightmare. Many simply stopped upgrading.

Problem
🧩

Platform Fragmentation

SAP had SCP for development, SAP Data Hub for data, SAP Analytics Cloud for BI, AI Business Services separately — each with its own portal, billing, and identity system. Architects couldn't build coherent solutions.

Problem
🔌

On-Premise Integration Debt

SAP PI/PO (Process Integration/Orchestration) required on-premise servers, Java stack expertise, and manual adapter maintenance. Connecting to cloud SaaS apps was painful.

Problem
🤖

Innovation Inaccessibility

AI, ML, low-code tools, and event-driven patterns were locked behind separate products. Business users couldn't automate; developers couldn't easily access AI models within SAP context.

Chapter 1

The 20-Year Evolution

From on-premise middleware to cloud-native platform — trace the lineage to understand why BTP works the way it does.

2004
SAP NetWeaver
First unified technology stack — SOA middleware for SAP Business Suite. Combined ABAP + Java in one platform. Think of it as the "operating system" for SAP ERP. Built on TopTier Software (acquired 2001). Final version 7.5 (2015), maintenance ends 2027.
2011
SAP HANA
In-memory columnar database. The "game changer" — real-time analytics on transactional data without separate warehouse. By 2013, full Business Suite ran on HANA. Forced SAP to rethink everything around in-memory computing.
2012
SAP HANA Cloud Platform (HCP)
First PaaS — launched as "SAP NetWeaver Cloud" in Oct 2012, rebranded May 2013. Java-based cloud development with HANA integration. 4,000+ customers and 500+ partners by 2015. The first attempt at "extend SAP in the cloud."
2015
SAP S/4HANA
Next-gen ERP built natively for HANA. Simplified data model, real-time processing. This is the "application" that BTP exists to extend and connect. The move to S/4HANA created the urgency for a cloud extension platform.
2017
SAP Cloud Platform (SCP)
Dropped "HANA" from name — signaling the platform is broader than one database. Added Cloud Foundry runtime, multi-cloud (AWS, Azure, GCP), expanded service catalog with integration, data, and AI/ML services.
2020
Cloud-First Pivot
CEO Christian Klein announces all innovation goes cloud-only. Stock drops 23-30% in one day. The market was skeptical, but this decision made BTP the mandatory innovation vehicle. No more on-premise-first development.
2021
SAP BTP Launched
Not just a rebrand — consolidated SCP + HANA Cloud + Analytics Cloud + Data Warehouse Cloud + AI under one umbrella. RISE with SAP launched simultaneously, bundling S/4HANA Cloud + BTP. Five pillars architecture.
2024–26
AI & Business Data Cloud Era
Joule AI copilot, Generative AI Hub, SAP Business Data Cloud (with Databricks), BTPEA replaces CPEA, scenario-based certification. Cloud revenue hits €17.14B. SAP Build Apps deprecated March 2026. All innovation is cloud-only.

The Five Pillars of SAP BTP

Think of BTP as a building with five load-bearing pillars on a multi-cloud foundation. Each pillar bundles related services. Click each to explore.

① Application Development & Automation

Build, extend, and automate
›

Why it exists: Enterprises need to build custom apps and automate processes without modifying SAP core. This pillar provides everything from pro-code to no-code to AI-assisted development.

Key mental model: "If I were building a startup on top of SAP data and processes, what tools would I need?" — this pillar is the answer.

Core services:

Analogy: Cloud Foundry = AWS Elastic Beanstalk. Kyma = managed EKS/AKS. ABAP Env = "ABAP in the cloud without SAP ERP." CAP = an opinionated Spring Boot/NestJS for SAP data.

② Integration

Connect everything
›

Why it exists: The average enterprise uses 187 SaaS apps. SAP alone has dozens of products. Without integration, data lives in silos and processes break across system boundaries.

Key mental model: Integration Suite is SAP's answer to MuleSoft/Boomi, but with 10,500+ pre-built SAP-specific integration flows that would take you months to build manually.

Core services:

Cloud Integration (CPI)API ManagementIntegration AdvisorOpen ConnectorsTrading Partner MgmtEdge Integration CellEvent MeshAdvanced Event Mesh

Critical framework — ISA-M: The Integration Solution Advisory Methodology is a structured approach for mapping integration domains (A2A, B2B, B2G, cloud-to-cloud) to the right integration style (process, data, event, thing). Heavily tested on the certification exam.

③ Data & Analytics

Unified data fabric
›

Why it exists: SAP systems generate massive transactional data, but it's trapped in application-specific schemas. Business users need unified, semantically rich data for BI, planning, and AI.

Key mental model: HANA Cloud = the engine (columnar in-memory DB + vector engine for AI). Datasphere = the data fabric (brings together SAP + non-SAP data while preserving business context). SAP Analytics Cloud = the consumption layer (BI + planning + predictive).

Core services:

SAP HANA CloudSAP DatasphereSAP Analytics CloudBusiness Data CloudData Lake (Relational + Files)

2025 addition — Business Data Cloud: Partnership with Databricks. Built on Delta Lake/Medallion architecture with zero-copy data sharing. This is SAP's response to the modern data stack movement.

④ Artificial Intelligence

AI embedded in business process context
›

Why it exists: Generic AI lacks business context. SAP AI understands purchase orders, material movements, financial postings. The value is AI that "speaks SAP."

Key mental model: AI Core = infrastructure (like SageMaker). Generative AI Hub = governed LLM access (like Azure OpenAI Service but multi-model). Joule = the user-facing copilot that orchestrates it all within SAP workflows.

Core services:

SAP AI CoreAI LaunchpadGenerative AI HubJoule CopilotJoule Studio (Agents)

LLM access via Gen AI Hub: OpenAI, Google, Meta, Anthropic (Claude), Amazon, Mistral, and SAP's own RPT-1 model. Prompt management, grounding via HANA vector engine, and orchestration — all within SAP's governance and data privacy framework.

⑤ Platform Foundation

Multi-cloud infrastructure & governance
›

Why it exists: All pillars sit on this shared foundation. It provides identity, security, connectivity, account management, and the multi-cloud abstraction layer.

Key mental model: The Global Account is your "AWS Organization." Subaccounts are your "AWS Accounts." Entitlements are IAM policies for service access. Cloud Connector is your "VPN tunnel" to on-premise.

Core services:

BTP CockpitIdentity Auth Service (IAS)Identity Provisioning (IPS)Destination ServiceConnectivity ServiceCloud ConnectorSAP Private LinkAudit LogAlert Notification

Chapter 5

Key Services Deep Dive

Master these services to think like a solution architect. Use the tabs to explore each domain.

SAP Integration Suite

The integration backbone — 10,500+ pre-built flows, 160+ connectors, Gartner Leader 6 years running.

Cloud Integration (CPI)

Message-based, API-based, and event-based integration flows. Visual flow designer. The "workhorse" — handles A2A, B2B, and cloud-to-cloud patterns. Think of it as a managed Apache Camel with SAP adapters.

API Management

Proxify APIs with rate limiting, analytics, monetization, and developer portal. Like Apigee or Kong but integrated with SAP's API catalog. Required for exposing SAP APIs to third parties.

Integration Advisor

ML-powered B2B mapping tool. Accelerates EDI/EDIFACT/ANSI X12 mapping development by suggesting field mappings based on learned patterns. A time saver for supply chain integration.

Event Mesh & Advanced Event Mesh

Event Mesh: basic pub/sub for SAP events. Advanced Event Mesh (Solace-based): enterprise-grade event streaming across multi-cloud with guaranteed delivery, topic routing, and replay. Use AEM for mission-critical event-driven architectures.

Edge Integration Cell

Run integration flows on-premise or at the edge, managed centrally from the cloud. Solves data residency, latency, and compliance requirements. The bridge for "cloud management, on-premise execution."

Open Connectors

170+ pre-built connectors for non-SAP cloud apps (Salesforce, ServiceNow, Slack, etc.). Normalizes third-party APIs into a consistent REST interface. Useful for rapid integration without custom adapter development.

SAP Build

From pro-code to no-code — the unified development and automation platform.

SAP Build Code

Pro-code development in SAP Business Application Studio with Joule AI code generation. CAP project scaffolding, OData service creation, SAPUI5/Fiori development. The "VS Code for SAP" with AI superpowers.

Build Process Automation

Workflow + RPA + Decision management in one service. Automate approvals, data extraction from PDFs (Document Information Extraction), and decision rules. Replaces SAP Workflow and iRPA as separate products.

Build Work Zone

Standard: Fiori Launchpad in the cloud — role-based app access with federation. Advanced: Full digital workplace with workspaces, knowledge bases, cards, and collaboration. The "front door" for all SAP apps.

⚠️ Build Apps — Deprecated

The no-code visual app builder was deprecated in March 2026. Capabilities are being consolidated into the unified SAP Build platform. Existing apps remain functional during the sunset period, but new projects should use Build Code or Fiori Elements.

SAP HANA Cloud

The in-memory data foundation — now with vector engine for AI and knowledge graph.

Three-Tier Architecture

In-Memory DB: Columnar store with vector engine for RAG (retrieval-augmented generation) and knowledge graph engine. The "hot" tier for real-time queries and AI embeddings.

Data Lake Relational Engine: Disk-based columnar store for warm data. 10× cheaper than in-memory. Supports standard SQL. Good for historical data and large analytical datasets.

Data Lake Files: Object storage for raw files (CSV, Parquet, JSON). The "cold" tier. Cheapest option for staging and archival.

Why Vector Engine Matters

Traditional databases store structured data. Vector engines store embeddings — mathematical representations of text, images, or documents. This enables:

• Semantic search over enterprise documents

• RAG — grounding LLM responses in your actual SAP data

• Knowledge graphs — connecting entities across business processes

Having this built into HANA Cloud means you don't need a separate Pinecone/Weaviate for enterprise AI applications.

SAP Datasphere & Analytics Cloud

Data fabric + BI/Planning — the "sense-making" layer for enterprise data.

SAP Datasphere

A data fabric — not just a data warehouse. It connects to SAP and non-SAP systems, preserves SAP business semantics (cost centers, profit centers, org structures), and provides a semantic layer accessible by multiple tools.

Key concepts: Spaces (logical data areas), Connections (50+ sources), Transformation Flows, Graphical Views, and the Business Builder (no-code semantic modeling).

With Business Data Cloud (2025): Native Databricks integration with zero-copy data sharing over Delta Lake. You can query SAP data in Databricks and Databricks data in Datasphere without moving data.

SAP Analytics Cloud (SAC)

Unified BI + Planning + Predictive in one cloud service. Key differentiator: you can plan and analyze in the same tool (not separate Tableau + Anaplan).

Smart features: Smart Insights (automated anomaly detection), Smart Predict (automated ML), Just Ask (natural language queries), and embedded Joule for AI-assisted analysis.

Live vs. Import models: Live connects directly to HANA/BW without data duplication. Import brings data into SAC's in-memory engine. Choose based on data freshness vs. performance needs.

Chapter 6

Development Models & Clean Core

CAP — Cloud Application Programming Model

SAP's opinionated framework for building enterprise services. Think of it as "Rails/Django for SAP" — heavy convention over configuration.

Core idea: You write CDS (Core Data Services) files that declaratively define your data model and service layer. CAP generates the OData API, database schema, and Fiori UI annotations from this single source of truth.

100 lines of CDS replaces thousands of lines of manual OData service implementation. You only write custom logic via event handlers (before/on/after hooks).

Supports: Node.js or Java (Spring Boot). Database-agnostic: HANA, PostgreSQL, SQLite. Deploy to Cloud Foundry or Kyma. Built-in multitenancy, authentication, localization.

// Define a data model in CDS
entity Books {
  key ID : UUID;
  title : String(100);
  author : Association to Authors;
  price : Decimal(9,2);
}

// Expose as OData service
service CatalogService {
  entity Books as projection on my.Books;
}

The fundamental principle: Extensions should never break upgrades, and upgrades should never break extensions.

Chapter 8

Commercial Models & Cost Architecture

BTPEA / CPEA — Prepaid Credit Pool

Your organization pre-purchases a pool of cloud credits (minimum ~$10K–$20K/year). Any eligible BTP service draws from this shared pool monthly. Volume discounts vs. PAYG pricing.

Pros

Volume discounts (often 15-30% off list). Flexibility to try new services without separate procurement. One contract covers everything. Automatic entitlements to all eligible services.

Cons

Unused credits expire at contract end (no standard rollover). Overage charges at full list price. Requires accurate capacity planning. Annual 3-5% escalation clauses common.

BTPEA vs. CPEA: BTPEA (April 2024+) is the successor. Expanded scope includes SAP Analytics Cloud. All new services and innovations only added to BTPEA. New customers get BTPEA; existing CPEA customers should plan migration.

Pay-As-You-Go — Zero Commitment

No upfront commitment. Pay monthly at standard list prices. Ideal for proof-of-concepts, pilots, and unpredictable workloads.

Key advantage: Can be seamlessly converted to CPEA/BTPEA while preserving all services, subaccounts, and data. SAP explicitly encourages "try before you commit."

Free Tier — 90+ Services, No Time Limit

Limited capacity on 90+ services within productive accounts (PAYG or BTPEA). Unlike the old trial (90 days), free tier has no expiration and can be upgraded to paid plans.

Gotcha: HANA Cloud free tier databases auto-stop every night. Must be manually restarted. Not suitable for "always-on" scenarios.

Best use: Development, learning, and PoC environments. Get hands-on without any cost.

Cost Optimization Strategies

Right-Size by Stage

Free tier for dev. PAYG for QA with usage controls. BTPEA for production with negotiated discounts. Every tenant (dev/QA/prod) costs separately — plan for 3× base cost.

Stop Non-Prod Instances

Shut down HANA Cloud and Kyma in dev/QA on nights and weekends. Use BTP CLI scripts or CI/CD pipelines to automate start/stop schedules. 60-70% savings on non-prod compute.

Negotiate Smart

Request credit rollover provisions. Cap overage rates at contract rates (not list). Lock in multi-year pricing to avoid annual escalation. Consider hyperscaler marketplace for committed-spend counting.

Monitor Continuously

Use SAP's open-source BTP Resource Consumption Monitor (GitHub). Set alerts at 80% credit utilization. Review monthly consumption reports in BTP Cockpit. Track cost per integration flow, per HANA GB.

1. A customer wants to add a custom field to the Sales Order in S/4HANA Cloud, Public Edition. No complex logic is needed. Which extensibility approach should a solution architect recommend?
Side-by-side extension on BTP using CAP
Key User Extensibility (in-app)
Developer Extensibility using RAP in ABAP Environment
Classic modification with access key
For simple custom fields without complex logic, Key User Extensibility is the lightest-weight approach. It requires no coding, runs in-app, and follows clean core Level A principles. Side-by-side would be over-engineering; developer extensibility is for more complex scenarios; classic modifications are not available in S/4HANA Cloud Public Edition.
2. An architect needs to connect a BTP application to an on-premise SAP ECC system. Which connectivity path is correct?
BTP App → Private Link → ECC
BTP App → Destination Service (Internet proxy) → ECC
BTP App → Destination Service → Connectivity Service → Cloud Connector → ECC
BTP App → API Management → ECC
The correct on-premise connectivity chain is: Destination Service (stores connection config) → Connectivity Service (routes to Cloud Connector) → Cloud Connector (secure reverse-invoke TLS tunnel) → On-premise system. Private Link is for hyperscaler-private connectivity, not general on-premise. Direct internet access to on-premise systems would be a security risk.
3. In the ISA-M framework, which integration style would you use for real-time order status notifications from S/4HANA Cloud to a custom BTP application?
Process Integration (synchronous API call)
Event Integration (publish/subscribe)
Data Integration (batch replication)
Thing Integration (IoT)
Real-time notifications are the textbook use case for Event Integration using SAP Event Mesh or Advanced Event Mesh. S/4HANA publishes 600+ business events natively via the Enterprise Event Enablement framework. The "notify-then-fetch" pattern applies: receive a lightweight event, then call back via OData API for full details. Process integration would require polling; data integration is for bulk movement.
4. A customer has unpredictable BTP usage and wants to pilot three services before committing. Which commercial model should they start with?
BTPEA with minimum commitment
Pay-As-You-Go (PAYG)
Individual service subscriptions
Free Tier only
PAYG is designed for exactly this scenario — zero upfront commitment, monthly billing, and seamless conversion to BTPEA later while preserving all services, subaccounts, and data. Free Tier alone is too limited for piloting real workloads. BTPEA requires commitment upfront. Individual subscriptions lack the flexibility to try multiple services easily.
5. Which SAP BTP runtime would you recommend for a team that wants to deploy containerized microservices with autoscaling, service mesh, and serverless functions?
Cloud Foundry
Kyma
ABAP Environment
SAP Build Code
Kyma is the fully managed Kubernetes runtime that provides all three: container orchestration with autoscaling (HPA/VPA), Istio service mesh, and serverless Kyma Functions. Cloud Foundry uses buildpacks (not containers directly) and lacks service mesh. ABAP Environment is for ABAP developers only. SAP Build Code is an IDE, not a runtime.
