Chapter 00 — The Origin Story

Why Does SAP BTP Exist?

Before learning how to administer BTP, understand the forces that created it — the problems, the historical workarounds, and why nothing else could solve them.

The Core Problem
Imagine you're an enterprise running SAP ERP for 15 years. Your system has 5 million lines of custom ABAP code, 200+ point-to-point interfaces, and modifications touching nearly every transaction. Now SAP says: "Move to S/4HANA Cloud — but you can't bring your custom code." Where does all that logic go? That's the problem BTP solves.

🏗️ What was done historically?

+
Before BTP, SAP administration meant BASIS. A dedicated team of SAP Basis administrators managed on-premise SAP systems — installing patches, tuning database performance, managing user accounts in transaction SU01, configuring RFC connections, monitoring with SM21/ST22, and transporting changes through the landscape with STMS.

Integration was handled by SAP PI/PO (Process Integration / Process Orchestration) — a heavyweight middleware requiring its own Java stack. Custom logic lived inside the ERP as ABAP modifications, user exits, BAdIs, and enhancement points. Every upgrade required regression testing of all custom code.

This worked for decades, but created massive technical debt. Organizations couldn't upgrade easily, couldn't adopt cloud, and couldn't innovate without risking their core business processes.

🔧 What problem does BTP solve?

+
BTP solves five interconnected problems:

1. Extension without modification — Build custom logic alongside SAP core ("side-by-side") instead of modifying it. This is SAP's "Clean Core" strategy.

2. Integration across the landscape — Connect SAP-to-SAP, SAP-to-third-party, cloud-to-on-premise through a single governed platform instead of hundreds of point-to-point interfaces.

3. Innovation access — AI, machine learning, IoT, process automation, low-code development — all available as managed services without building infrastructure.

4. Multi-cloud flexibility — Run on AWS, Azure, or GCP depending on your existing cloud investments and data residency requirements.

5. Unified governance — One account model, one identity layer, one commercial agreement across all these capabilities.

🤔 What would I use instead?

+
Without BTP, you'd need a patchwork of tools:

IntegrationMuleSoft or Boomi ($100K+/year)
DataSnowflake or BigQuery
Low-CodePower Platform or Mendix
AI/MLAWS SageMaker or Azure AI
RuntimeSelf-managed Kubernetes
IdentityOkta or Azure AD custom config
ConnectivityCustom VPN + API gateways

Critically, none of these natively understand SAP's business data models — organizational hierarchies, currency handling, material masters, transaction semantics. Every integration requires custom mapping that BTP provides out of the box.

🎯 When should I use BTP?

+
Use BTP when:
• You run SAP and need to extend or integrate it with cloud services
• You're migrating to S/4HANA Cloud and need a home for custom logic
• You want managed services for AI, integration, or low-code that understand SAP data
• You need a governed platform for multiple dev teams building on SAP

Consider alternatives when:
• You have zero SAP footprint (hyperscaler-native tools may be simpler)
• You need deep non-SAP integration only (MuleSoft has broader connector ecosystems for non-SAP)
• You're building consumer-facing apps with no SAP backend dependency
🧠 Knowledge Check: Why is BTP essential for S/4HANA Cloud migrations?

The "Clean Core" strategy means keeping S/4HANA Cloud as close to standard as possible. All customizations — extensions, integrations, automations — are built on BTP using governed APIs, ensuring smooth upgrades and innovation cycles.
Chapter 01 — The Evolution

From HANA Cloud Platform to BTP

A decade of strategic pivots — each rebrand reflecting a fundamental shift in SAP's cloud architecture and ambition.

Jun 2011
SAP HANA Ships
The in-memory database launches at SAPPHIRE NOW. It's a database product, not a platform — but it plants the seed for everything that follows. The speed of HANA makes real-time analytics on transactional data possible for the first time.
Oct 2012
SAP NetWeaver Cloud (First PaaS)
SAP's first attempt at Platform-as-a-Service. Runs in SAP's own data centers on the proprietary Neo environment. Supports Java and HANA XS development. Quickly renamed to avoid confusion with on-premise NetWeaver.
May 2013
SAP HANA Cloud Platform (HCP)
The HANA brand is hot. SAP leans into it, positioning HCP as the way to build cloud apps on HANA. Still Neo-only, still SAP data centers only. Reaches 4,000+ customers by 2015, but the proprietary lock-in becomes a problem.
Feb 2017
SAP Cloud Platform (SCP)
Renamed at Mobile World Congress. The key insight: this platform is more than HANA. In 2017–2018, SCP introduces the Cloud Foundry environment — embracing open-source, deploying on AWS, Azure, and GCP for the first time. This is the pivotal architectural shift from proprietary to open, multi-cloud.
2018
ABAP Environment ("Steampunk")
SAP creates a cloud-native ABAP runtime using the RESTful Application Programming Model (RAP). For the first time, ABAP developers can build cloud applications using modern patterns while leveraging their existing skills. A bridge between old and new worlds.
2019
Kyma Runtime Added
Kubernetes-based runtime joins the platform, based on the open-source Kyma project. Now SCP offers three environments: Neo (legacy), Cloud Foundry (mainstream), and Kyma (cloud-native). Event-driven architectures become first-class citizens.
Jan 2021
SAP Business Technology Platform
The final (current) brand. SCP merges with HANA Cloud, Analytics Cloud, Data Intelligence, and Integration Suite under the BTP umbrella. Coincides with RISE with SAP — SAP's business transformation offering that bundles S/4HANA Cloud + BTP. The message: BTP is the technology foundation for all SAP innovation.
2022–2023
SAP Build & Generative AI
SAP Build portfolio (Apps, Process Automation, Work Zone) brings low-code/no-code. SAP AI Core and Generative AI Hub launch. Joule copilot integrated across SAP applications. BTP becomes the AI and automation hub.
Dec 2028
Neo Environment Sunset
The original proprietary runtime is scheduled for end-of-life. All customers must migrate to the multi-cloud foundation (Cloud Foundry or Kyma). An era ends — and the multi-cloud future is fully realized.
Key Insight
Every rebrand reflects a real architectural shift: HCP → SCP added multi-cloud. SCP → BTP unified the full technology stack. Understanding this evolution helps you understand why BTP is structured the way it is today — and why Neo, Cloud Foundry, and Kyma coexist.

Entitlement vs Quota
Entitlement = your right to use a service plan. Quota = how much of it you can use. Example: You're entitled to the "Cloud Foundry Runtime" service, with a quota of 4 units of memory. You assign 2 units to DEV subaccount and 2 to PROD.
🧠 Knowledge Check: What is the relationship between a subaccount and a Cloud Foundry Organization?
AOne subaccount can contain multiple CF Organizations
BEnabling CF in a subaccount creates exactly one CF Org (1:1 mapping)
CCF Organizations exist independently of subaccounts
DSubaccounts and CF Orgs are the same thing
When you enable Cloud Foundry in a subaccount, it automatically creates one CF Organization. Within that Org, you create Spaces (dev, test, prod) for further logical separation. The Org inherits the subaccount's region and cannot span multiple subaccounts.

☁️ Cloud Foundry — The Managed PaaS

Cloud Foundry is the most widely used BTP runtime. Think of it as a managed application hosting platform — you push your code, CF packages it into a container using a buildpack, deploys it, manages networking, and handles scaling. You never touch a Dockerfile or Kubernetes manifest.

Why it exists: Most SAP extension developers want to write business logic, not manage infrastructure. CF lets you cf push myapp and it just works — similar to Heroku, but integrated with SAP services.

Organizational model: When you enable CF in a subaccount, it creates an Org. Within the Org, you create Spaces (dev, test, prod). Each Space has its own apps, service instances, and member permissions.

How apps deploy: The primary method is Multi-Target Applications (MTAs) — a descriptor file (mta.yaml) defines your app modules, service dependencies, and deployment sequence. Deploy with cf deploy.

⚓ Kyma — The Kubernetes Runtime

Kyma is a managed Kubernetes cluster provisioned by SAP Gardener, enriched with additional modules: Istio service mesh, serverless functions (scale-to-zero), and event-driven architecture for reacting to SAP business events.

Why it exists: Cloud Foundry abstracts too much for teams that need full container control, custom networking, sidecar proxies, or event-driven microservices. Kyma gives you Kubernetes power with SAP integration built in.

When to choose Kyma over CF: When you already have K8s expertise, need containers with custom base images, want service mesh capabilities, or are building event-driven extensions that react to SAP S/4HANA business events in real-time.

Key difference from raw K8s: Kyma clusters come pre-configured with SAP service bindings, event subscriptions, and identity integration. You don't need to build the SAP connectivity layer yourself.

🔷 ABAP Environment — Steampunk

A cloud-native ABAP runtime using the ABAP RESTful Application Programming Model (RAP). "Steampunk" is its internal codename — modern cloud engineering principles applied to the 40-year-old ABAP language.

Why it exists: There are millions of ABAP developers worldwide. Rather than forcing them to learn Java or Node.js, SAP created a cloud ABAP environment with modern patterns: CDS views, behavior definitions, service bindings, and only released APIs.

Key restriction: You can only use released APIs and objects. No direct database table access, no classic dynpros, no unreleased function modules. This constraint is what makes it "cloud-ready."

Sizing: Measured in ABAP Compute Units (ACU) for processing power and HANA Compute Units (HCU) for database. Systems can be hibernated to save costs during non-business hours.

🧭 Decision Guide: Which Environment?

Ask these questions to choose:

→ Cloud Foundry if: your team writes Java/Node.js/Python, you want managed PaaS simplicity, you're building SAP Fiori apps with CAP (Cloud Application Programming model), or you just want the fastest path to deployment.

→ Kyma if: your team has Kubernetes expertise, you need container-level control, you're building event-driven microservices, or you need service mesh / advanced networking.

→ ABAP Environment if: your team are ABAP experts, you're building extensions for ABAP-based SAP products (S/4HANA, ECC), or you want to use the RAP programming model.

→ Multiple environments: You can enable all three in the same subaccount. A common pattern is CF for web apps + ABAP for backend extensions, or CF for BTP services + Kyma for event processing.

Chapter 04 — Identity & Access Management

Who Can Do What, and How They Prove It

The identity layer is the most conceptually dense part of BTP administration. Here's the full picture.

👤 Platform Users

Administrators, developers, and operators who manage the BTP platform itself. They work in the BTP Cockpit, use CLI tools, deploy applications, and manage services. They interact with the platform layer.

Authenticate viaSAP ID Service (default) or custom IdP
Manage atGlobal account, directory, subaccount levels
PermissionsRole collections assigned in Cockpit

👥 Business Users

End users who consume applications deployed on BTP — SAP Build Work Zone, Fiori apps, custom apps. They never see the Cockpit. They interact with the application layer.

Authenticate viaSAP Cloud Identity Services (IAS)
Authorized byXSUAA role collections or IAS policies
Provisioned byIPS (Identity Provisioning Service)

Why this layered model?
Developers define scopes and role templates in their application code (xs-security.json). Administrators then create role collections in the Cockpit and assign them to users — without needing to understand the application's internal authorization logic. This separation of concerns is key.

🔐 IAS — Identity Authentication

Cloud-based authentication service. Handles SSO, MFA, risk-based auth, social login. Supports SAML 2.0 and OpenID Connect. Can act as a proxy to your corporate IdP (Azure AD, Okta, ADFS).

Key insight: SAP recommends IAS as an intermediary even when you have a corporate IdP. This gives you centralized configuration, attribute enrichment, and consistent security policies across all SAP apps.

🔄 IPS — Identity Provisioning

Automates user lifecycle: create, update, disable, delete users across systems. Uses SCIM 2.0 protocol. Connects source systems (HR, Azure AD) to target systems (IAS, BTP subaccounts, S/4HANA Cloud). 70+ pre-built connectors.

Global User ID: A unique identifier that follows users across all SAP systems, enabling consistent identity across the entire landscape.

🎫 XSUAA — Authorization Server

SAP's extension of Cloud Foundry UAA. An OAuth 2.0 authorization server that issues JWT tokens. Does not store users — relies on trusted identity providers. Manages scopes, roles, and role collections for application-level authorization.

Key distinction: IAS handles authentication (who are you?). XSUAA handles authorization (what can you do?).

Chapter 05 — The Admin Toolchain

Cockpit, CLIs, and Terraform

Four tools for four levels of automation — from clicking in a browser to infrastructure-as-code.

🖥️ BTP Cockpit

GUI — Point & Click

Web UI for visual administration. Best for exploration, initial setup, and tasks where you need to see the full picture. URL pattern: https://<region>.cockpit.btp.cloud.sap

⌨️ btp CLI

CLI — Account-Level

Command-line for global account, directory, subaccount, entitlement, and security management. Scriptable. Pattern: btp [action] [group]/[object]

🔧 cf CLI

CLI — CF Environment

Manages Cloud Foundry runtime: apps, services, routes, logs. Once btp CLI creates the CF org, cf CLI takes over for everything inside it.

🏗️ Terraform

IaC — Declarative

Infrastructure as Code using the SAP BTP Terraform Provider. Declare desired state in .tf files, Terraform reconciles. Best for repeatable multi-environment (DEV/QA/PROD) provisioning.

The CLI Handoff Pattern
btp CLI manages the account layer (subaccounts, entitlements, trust). Once an environment is created, you switch tools: cf CLI for Cloud Foundry, kubectl for Kyma, ADT for ABAP. Think of btp CLI as the "landlord" tool and cf/kubectl as the "tenant" tools.
Chapter 06 — Connectivity

Bridging Cloud and On-Premise

Most SAP customers have critical systems behind their firewall. BTP needs to reach them — securely.

🔌 SAP Cloud Connector

CLOUD ←→ ON-PREMISE

A lightweight agent installed in your on-premise network. Creates a reverse invoke proxy — the connection is always initiated outbound from your network to BTP via TLS. No inbound firewall ports needed.

ArchitectureMaster/Shadow for high availability
ProtocolsHTTP/S, RFC, TCP
SecurityWhitelist specific paths & services
MappingVirtual host:port → real internal address
AdminWeb UI on port 8443
Use WhenConnecting to on-prem SAP (ECC, BW, PI)

🔗 SAP Private Link

CLOUD ←→ CLOUD (PRIVATE)

Uses native hyperscaler private networking (Azure Private Link, AWS PrivateLink) to establish connections between BTP and your cloud resources. Traffic never leaves the hyperscaler backbone.

ArchitectureNative hyperscaler private endpoints
SupportsAzure, AWS
Use WhenBTP → your VPC/VNet resources
AdvantageNo public internet, lower latency

📍 Destination Service

CONNECTION CONFIGURATION

A centralized registry for connection configurations. A Destination stores the URL, authentication method, and proxy type for a target system. Applications look up destinations at runtime — no hardcoded endpoints.

LevelsSubaccount, service instance, environment
Auth TypesBasic, OAuth, SAML, Client Cert, Principal Propagation
Proxy TypeInternet, OnPremise (via Cloud Connector)
AnalogyLike a DNS + credential vault for backends
Chapter 07 — Observability & DevOps

Monitoring, Alerting, and Lifecycle

An administrator's core job after setup: know what's happening, react when things break, transport changes safely.

BTP observability operates at two levels — central (across the whole landscape) and local (within a subaccount).

🏢 SAP Cloud ALM (Central)

The central operations hub for your entire SAP landscape. Provides health monitoring, business process monitoring, integration monitoring, user monitoring, and intelligent event processing. Think of it as your "single pane of glass" for all SAP systems.

🔔 Alert Notification (Local)

Event-based alerting within BTP. Three concepts: Actions (where to notify — email, Slack, webhook), Conditions (what to filter), Subscriptions (bind actions to conditions). Can trigger SAP Automation Pilot for auto-remediation.

📋 Audit Log Service

Security-relevant event logging: who accessed what, who changed what, and when. Essential for GDPR, SOX compliance. Standard plan retains 90 days. Access via Audit Log Viewer UI or Retrieval API.

📊 SAP Cloud Logging

OpenSearch-based logging service for BTP applications and services. Centralized log aggregation, search, analysis, and visualization. The "ELK stack" equivalent within BTP.

📦 Cloud Transport Management (cTMS)

Transports content across BTP landscapes (DEV → QA → PROD). Supports MTA archives, Integration Suite content, and other BTP artifacts. Configure transport routes, nodes, and approval workflows — similar in concept to the classic STMS but for the cloud world.

🔄 CI/CD Service

SAP's managed CI/CD pipeline service. Define build, test, and deploy stages. Integrates with Git repositories (GitHub, GitLab, Bitbucket). Pre-built pipeline templates for CAP, Fiori, and MTA projects. Can also use external CI/CD (Jenkins, Azure DevOps, GitHub Actions).

Trial: Non-commercial, 90-day limit, no SLA, restricted services. Work is deleted when it expires.

Region Naming Convention
Region codes follow a pattern: eu10 = Europe, AWS (#10 series). eu20 = Europe, Azure (#20 series). eu30 = Europe, GCP (#30 series). The first part is geography, the number indicates the hyperscaler. You choose a region when creating a subaccount — and it's immutable.
